# Scope check: could schedule waiting rescue the 16 rejected states?

2026-09-20. Read-only audit, no new simulator run or repo code changes. `audit_waiting_opportunity.py` verifies all 48 captured state/event/decision hashes against the exact replay receipt, then inspects request timestamps. Result: `waiting-opportunity-audit.json`, all 16 states have all known earliest-pickup times at or before current decision time. Incoming event types are exclusively requestArrived, vehicleAdvanced and timerTick. Historical inactive requests are included too, making this a stronger timestamp check than filtering only active riders.

Source inspection: `PhysicalPlanValidator` and `RouteScheduleProjector` add nonnegative travel and service time, and wait only when pickup is before its earliest bound. `OriginHoldCandidateTransformer` relocates existing first-pickup waiting; it cannot create a new scheduling solution by delaying arbitrary pickups.

For a fixed structurally valid route in these snapshots, with travel times fixed during evaluation and no unopened windows, the no-wait schedule minimizes each stop's absolute time. For a not-yet-picked rider, the interval from pickup to drop consists of the same travel/service terms plus any inserted waits between those stops. Delaying before pickup cannot remove a forced later wait because none exists; it only shifts the interval. Waiting within that interval increases ride time. An onboard rider's pickup time is already fixed, so waiting cannot improve their ride time either. Thus added waiting cannot cure an earliest-schedule pickup-window or maximum-ride-time violation for this family. Precedence failures likewise cannot be repaired by timing.

The 9 physically valid routes already have positive delay blockers in the commitment audit. Added waiting cannot lower those ETA values. Therefore neither the physically failed routes nor those 9 survivors provide a waiting-based rescue under the fixed route/assignment/travel/state model examined here.

This is a bounded reasoning result tied to the timestamp evidence and fixed-snapshot model. It is not a general DARP infeasibility proof and does not rule out waiting before future information arrives, different travel realizations, alternative vehicle assignments, changed initial promises, advance reservations, or earlier trajectory choices. It does not certify execution in FleetPy. No claim that arbitrary waiting is generally useless.
